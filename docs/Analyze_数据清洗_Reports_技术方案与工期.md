# Analyze / 数据清洗 / Reports —— 技术方案、工作量(人日)与开发周期

> 范围：假设三模块**全部自建**。
> 已确认前提：① 工作量以**人日(person-day)**计；② OLAP/查询引擎**由数据组定**（本文按"需引入一套标准 OLAP，如 ClickHouse/Doris/StarRocks"中性假设，并标注"接现成"可省的量）；③ Analyze 与 Reports **以效果归因为主**，自助 BI 探索降配后置。
> 数据底座：已有 **App SDK 端内打点**（event + 属性 + 用户标识；无 email）。时区统一 **Asia/Dubai (UTC+4)**。

---

## 0. 总体架构（三模块如何咬合）

```
端内SDK埋点 ──► [实时接入Kafka] ──► ODS原始事件
                                      │
                       ┌──────────────┴───────────────┐
                       ▼ (T+1批/准实时)                 │
              【模块B 数据清洗】                          │
        ID-Mapping · 标准化 · 时区归一 · 去重             │
        用户宽表 / 事件宽表 / 标签层 / 衍生trait          │
                       │                                │
        ┌──────────────┼───────────────┐               │
        ▼              ▼                ▼               ▼
  【模块A Analyze】              【模块C Reports】   (圈人/编排/下发 复用同一宽表)
  行为·留存·漏斗·归因引擎  ◄──共享──► 活动报表·实验报表·订阅
                       │
                  统一 OLAP 查询层
```

**设计主线**：以「**统一事件宽表 + 归因数据模型**」为骨干。Analyze 的漏斗/归因引擎与 Reports 的活动/实验报表**共用同一套口径与查询层**，避免双算双口径。模块B（数据清洗）是另外两个模块的前置依赖。

---

## 1. 模块B：数据清洗（底座，优先级最高）

### 1.1 技术方案
| 子系统 | 方案 |
|---|---|
| 接入层 | SDK 事件 → 网关 → **Kafka**（实时）+ 落 ODS（批）。Schema Registry 管控事件契约。 |
| 事件字典/校验 | 事件元数据中心（event/属性的类型、必填、枚举），入库前校验+脏数据隔离。 |
| **ID-Mapping** | 无 email → 以 `customer_id`/手机号为主键；多端设备 ID ↔ 用户 ID 图谱（增量合并）。 |
| 标准化清洗 | 去重(幂等键)、纠偏(乱序/迟到事件水位线)、**时区统一 UAE**、属性规整、单位归一。 |
| 宽表层 | 用户宽表(画像/活跃/设备/来源) + 事件宽表(打平属性) + RFM 基础指标。 |
| **衍生标签框架** | 可配置聚合(Count/Sum/First-Last)+SQL 计算 → 生成 trait（CLV/活跃度/偏好），落标签表，**服务化供圈人/归因消费**。 |
| 编排/质量 | DAG 调度(Airflow/DolphinScheduler) + DQC(行数/空值/延迟/分布漂移)+ 告警。 |

### 1.2 工作量（人日）
| 任务 | 人日 |
|---|---|
| 接入层(Kafka+ODS落地) | 6 |
| 事件字典与校验/脏数据隔离 | 5 |
| ID-Mapping(主键策略+多端图谱) | 8 |
| 标准化清洗(去重/纠偏/时区/属性) | 8 |
| 用户宽表+事件宽表+RFM基础 | 10 |
| 衍生标签框架(可配置+SQL) | 12 |
| 标签服务化接口(供圈人/归因) | 5 |
| DAG调度编排 | 4 |
| 数据质量监控DQC+告警 | 5 |
| **小计** | **~63 人日** |

> 若数据组已有成熟数仓分层与调度，可省 8-12 人日（编排/部分落地）。

## 2. 模块A：Analyze（分析，效果归因为主）

### 2.1 技术方案
| 子系统 | 方案 |
|---|---|
| 查询抽象层 | 统一 Query DSL → 编译到 OLAP SQL；指标/维度语义层（保证与 Reports 同口径）。 |
| 行为分析 | 多事件趋势/对比，按属性 split、时间粒度。 |
| 留存分析 | First/Return Event；类型 **Unbounded / N-Day / First Occurrence**；split by；duration。 |
| **漏斗分析** | 多步有序/无序、转化窗口、分维度下钻、流失节点；按分群过滤。 |
| **归因引擎(核心)** | 活动/实验/触达 → 转化事件归因；归因窗口；模型 **首触/末触/线性/位置衰减**；**对照组增量**(global control group)；用户级归因明细 → 聚合。 |
| 保存/告警 | 分析存为模板复用；指标阈值 Set Alert。 |
| 前端 | 事件/维度选择器 + 图表(趋势/留存矩阵/漏斗) + 表格 + 下钻。 |

## 6. 开发周期（日历）

工期受**团队规模**和**模块依赖**双重影响。以一个**样例配置**换算（你可据实调整）：

**样例团队**：后端×2、数据工程×2、前端×2、QA×1 ≈ 7 人；按协作损耗后**有效产能 ≈ 4.5 人日/日**。

### 关键依赖
- 模块B（清洗）是 A/C 的**前置**——宽表/标签未就绪，Analyze 归因和 Reports 无数据可算。
- A 的归因引擎与 C 的报表**共享**，C 可在 A 的引擎成型后快速搭。

### 阶段计划（含重叠并行）

| 阶段 | 内容 | 日历 |
|---|---|---|
| **P0 准备/选型** | 数据组定 OLAP；冻结埋点 schema；ID-Mapping 方案；口径对齐 | **1–2 周** |
| **P1 数据清洗底座** | 模块B（接入→清洗→宽表→标签→DQC） | **4–5 周**(数据主导，前后端可提前搭框架) |
| **P2 Analyze+Reports 并行** | 模块A(漏斗/归因/前端) 与 模块C(活动/实验报表) 并行，依赖P1宽表 | **5–6 周** |
| **P3 联调/UAT/上线** | 三模块联调、数据准确性校验、灰度 | **2–3 周** |

- 阶段间有重叠（P1 后期 A/C 即可启动）。
- **整体日历 ≈ 11–14 周（约 3–3.5 个月）**。
- 若 OLAP 接现成 + 数仓分层已有：可压到 **≈ 9–11 周（约 2–2.5 个月）**。
- 若几乎从零建数据链路：拉长到 **≈ 16–18 周（约 4 个月）**。

## 7. 关键假设与最大摆动因子

1. **OLAP 选型（最大变量，±15–20 人日 / ±2–4 周）**：接现成 ClickHouse/Doris 最省；只有数仓备份需引入并建物化层；从零建链路最贵。**建议优先推动数据组拍板**。
2. **埋点 schema 稳定性**：若事件字典需大改/补埋点，P0 拉长，且清洗返工。
3. **归因口径需求方共识**：归因窗口、首/末触模型、对照组定义需 Growth 早确认，否则 A/C 返工。
4. **无 email**：ID-Mapping 以 customer_id/手机号为主键，多端打通是清洗模块的重点工作量。
5. **时区**：全链路统一 Asia/Dubai；排期/归因/报表口径一致。
6. 人日为**净开发**，未含需求评审、长尾运维；已在第5节给出 15% 缓冲建议。

## 8. 风险与建议
- **R1 依赖串行**：A/C 强依赖 B。建议 B 的"宽表/标签接口契约"在 P0 就定稿，让 A/C 团队**面向契约先开发 mock**，缩短串行等待。
- **R2 口径分裂**：Analyze 与 Reports 必须共用语义层与归因引擎，**严禁各算各的**，否则数据对不上是最常见上线事故。
- **R3 数据准确性**：P3 必须留足"数据校验"工时（与现有报表/抽样人工核对），归因类系统最怕"数字不可信"。
- **建议**：先做一个**最小闭环**(单活动→归因→活动报表)打通 B→A→C 全链路，再横向铺开漏斗/留存/实验报表，降低集成风险。
