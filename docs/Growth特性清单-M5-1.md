## 0. 模块定位
- **优先级**：P1（"千人千面/自建下发"，路径①首页活动位；可慢换，合同一年期、倾向不续约，row73/77）。
- **基线**：复刻 MoEngage 录屏视频2 实拍的 `Web & App (API)` 型 experience——三步向导（选人→内容→排期）+ `POST /experiences/fetch` 对等内容下发 API（视频）。
- **风险定位**：**风险最低、应优先验证**。路径①首页"千人千面"卡片本就只借 MoEngage 的下发能力（Botim 自有规则分组、客户端自渲染），**可自建**（row11/73）；自研对等 fetch API 后即可与 MoEngage 完全脱钩。建议在 Phase 1 即做可行性验证。
- **增量主线**：彻底去 MoEngage 依赖（路径①脱钩）+ 多语言 payload + 客户端自渲染/缓存降级 + 🤖AI(可选) 个性化内容/变体推荐（对齐 row6 "增量靠 AI"）。
- **现状事实**：首页分组 = Botim 自有规则分组后放入 MoEngage、仅借其下发能力（row11/73）；最常用关键功能之一 = "把配置信息下发到每个用户"（row21）；无 email、业务线 ID 未打通、无 CDP（row75）；客户端自渲染（API 型不在 MoEngage 渲染，视频）。

## 4. 依赖关系
### 4.1 技术依赖
- **M2 规则引擎 → 前置 M5**：命中判定（B1/B4）**复用 M2 同一规则引擎**做 audience 匹配，无 M2 则无法判定命中。
- **客户端 SDK 集成 → 前置 M5**：路径①客户端自渲染（D1–D3），需客户端团队配合渲染 + 缓存。

## 5. 前置阻塞与风险
- **R1 KV schema 归属未定** → payload 的 KV schema 由谁定义（前端约定 vs 配置驱动）未明，影响客户端渲染契约（C4，与客户端团队）。
- **R2 多语言文案来源** → 多语言 payload（C3）文案来源需与 M6 AI 文案衔接，否则只有壳无内容。
- **R3 fetch 接口实时性 SLA** → 首页加载需秒级，决定命中判定是否要做近实时（A7）；若要求近实时则命中复用 M2 的批量快照不够，需加重（row60/61）。
- **R4 customer_id 与各业务线 ID 映射** → 无 email 前提下（row75），identifiers 的 customer_id 与各业务线 ID 映射覆盖率/准确率决定命中可达性（A3，数据组）。
- **R5 客户端渲染/缓存就绪度** → 路径①完全依赖客户端自渲染 + 缓存（D1/D2），客户端团队排期与能力是落地开关。

## 6. Phase 落地建议
- **优先级 P1**，但因**"风险最低"**，建议在 **Phase 1 就做可行性验证**：路径①本就只借 MoEngage 下发、客户端自渲染、可自建（row73），是最干净的脱钩点。
- **Phase 1 验证目标**：先定义对等接口 `POST /experiences/fetch {identifiers, experience_key} → {payload}`，命中判定复用 M2 规则引擎，**打通首页一个卡片位**端到端（选人→内容→排期→fetch→客户端渲染），证明可脱离 MoEngage。
- **Phase 2+（对应重新分析 P-C，3–4 周）**：补全多 variation 分流(B3)、多语言 payload(C3)、缓存/降级(D2)、🤖AI 个性化推荐(B5)，横向铺开更多首页活动位。
- **建议顺序**：① 先与 Growth 对齐首页活动位规范 + experience_key 生命周期、与客户端团队对齐渲染/缓存方案 → ② Phase 1 打通一个卡片位的对等 fetch 验证脱钩可行性 → ③ Phase 2 扩多语言/多变体/AI 个性化。
