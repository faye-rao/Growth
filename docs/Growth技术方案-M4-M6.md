# M4 · Campaign 漏斗追踪 / 归因

## 1. 需求与约束回顾
复刻 MoEngage "查看→点击→转化"单活动漏斗（A1–A3）+ 1–2 天可配归因（B），并以 **跨产品漏斗（C，通话→Wallet→Remittance）** 作核心差异化正面回答"MoEngage 答不了的问题"。算料来自 M8 触达/转化日志宽表，跨产品漏斗强依赖 **M8 跨业务线 ID-mapping**（无 email→customer_id/手机号）。重型看板归数据组，我方只做追踪 + 轻呈现（NL2SQL / 轻看板）。口径未全公司统一（R1）是开发前置。

## 2. 候选技术方案（≥2）

- **方案 A：即席 SQL 窗口函数 / 会话化（funnel via window function + sessionization）**
  做法：在明细事件宽表上用 `ROW_NUMBER / LEAD / LAG` + 时间差判定排序与归因窗口，会话化后按 step 顺序聚合。漏斗定义即一段参数化 SQL，查时现算。
  适用：漏斗定义多变、探索期、活动量不大、对"任意维度下钻"诉求强；与 NL2SQL（text-to-SQL）天然契合。

- **方案 B：预计算 / 物化漏斗（离线预聚合固定漏斗，查时直读）**
  做法：对运营真正常看的 5–10 个固定漏斗，T+1 批跑预聚合成漏斗结果表 / 物化视图（user→step→time），查询只读结果。可叠加每日快照支撑留存。
  适用：固定漏斗、看板高频复看、对查询延迟敏感（轻看板秒开）；与 Botim T+1 主路线契合。

- **方案 C：OLAP 内置漏斗 / 留存函数（ClickHouse `windowFunnel` / `retention`、Apache Druid）**
  做法：把事件灌入列存 OLAP，用引擎内置的漏斗/留存算子在引擎侧高效完成步序判定，跨产品漏斗用 customer_id 在事件流里做跨业务线 JOIN / 同主键聚合。
  适用：事件量大、需交互式查询、漏斗+留存都要、跨产品漏斗这种重 JOIN/序列匹配场景。**Botim OLAP 未定，此方案与"先定 OLAP"绑定。**

## 3. 优劣对比表

| 维度 | A 即席 SQL 窗口 | B 预计算物化 | C OLAP 内置函数 |
|---|---|---|---|
| 实现成本 | 中（SQL 能力门槛，无需新组件） | 中（要建批作业 + 结果表治理） | 中-高（需先落 OLAP 选型/运维） |
| 性能·延迟 | 低（大数据量现算慢） | 高（直读结果毫秒-秒级） | 高（列存 + 内置算子最快） |
| 可扩展 | 中（任意漏斗灵活，但量大吃力） | 低（固定漏斗，新漏斗要新建作业） | 高（新漏斗改 SQL 即可，量大可扩） |
| 运维 | 高（依赖既有数仓，轻） | 中（批作业 + 结果表对账） | 低（多一套 OLAP 集群要养） |
| 对 Botim 适配度 | 中（探索/NL2SQL 友好，重看板不抗压） | 高（T+1 主路线 + 轻看板秒开 + 易对账 D3） | 高（跨产品漏斗最优解，但需先关 OLAP 未定） |

## 4. 业界典型做法
- **ClickHouse `windowFunnel()` / `retention()`**：增长分析事实标准，按 customer_id 在事件流里直接算步序与留存，跨产品只要同主键即可序列聚合。
- **Apache Druid + 序列/漏斗扩展**：交互式 OLAP，适合大事件量低延迟下钻。
- **Amplitude / Mixpanel 内部事件分析引擎**：产品级漏斗/留存/路径，本质是"事件流 + 列存 + 预聚合 + 序列匹配"的工程化封装——印证"预计算固定漏斗 + 引擎内置序列算子"是主流组合。

## 5. AI 新做法
- **多触点归因模型替代经验固定窗口**：Shapley value / Markov chain attribution 给跨触点贡献度分配，替代"1–2 天硬窗口"的粗口径（对应 D4 自动归因洞察）。Botim 起步用固定窗口兜底、AI 归因作增量复盘。
- **漏斗异常检测**：对漏斗各步转化率做时序异常告警，承接 D3"数字对得上"对账 + 差异告警。
- **自然语言问数（text-to-SQL）出漏斗**：复用 M2 NL2SQL，"说人话"生成漏斗 SQL（E1），降低看漏斗门槛。

## 6. 面向 Botim 的推荐选型
**接现成 OLAP、用 `windowFunnel` 算漏斗为主干，固定高频漏斗叠加 T+1 预计算物化，跨产品漏斗须等 M8 ID-mapping 打通后再上。** 具体：单活动漏斗（A1–A3）+ 留存先用 ClickHouse `windowFunnel/retention`（若 OLAP 选型短期不落地，则退化为方案 A 即席 SQL 在现有数仓兜底）；运营真常看的 5–10 个漏斗按方案 B 预计算成结果表，保证轻看板秒开并便于 D3 双跑对账；**跨产品漏斗（C）是差异化命门，但 customer_id 跨业务线映射覆盖率/准确率是硬前置——先关 R2（M8 ID-mapping）再开发，否则"数字对不上"反伤信任**。归因起步用可配固定窗口（B2），Shapley/Markov 与异常检测作 AI 增量后置。开发前先关 R1（口径统一），避免 A5/B 返工。

# M5 · 千人千面（自建下发 fetch）

## 1. 需求与约束回顾
复刻 MoEngage `Web & App (API)` 型 experience：对等 `POST /experiences/fetch`（A1）按 experience_key 返回该用户应得 payload，命中判定 **复用 M2 规则引擎**（B1），客户端自渲染（D1）。首页加载需 **秒级 SLA**（A7），但实时活动占比小、批量为主。多语言 payload（C3，印/菲/阿/英）衔接 M6。无 email→identifiers 以 customer_id/手机号为主键（A3），依赖 M8 ID-mapping。路径①本就只借下发、可自建，是**风险最低、应优先验证**的脱钩点。

## 2. 候选技术方案（≥2）

- **方案 A：请求时实时命中（fetch 时实时跑规则判定 audience+variation）**
  做法：fetch 到达时实时跑 M2 规则引擎判定命中 audience→分配 variation→组装 payload 返回。
  适用：人群定义变化快、强实时（行为触发型卡片）、用户量/QPS 可控；实时性最好但秒级 SLA 下规则求值压力大。

- **方案 B：预计算人群-experience 映射（离线算好，fetch 时 KV 查找）**
  做法：T+1 / 小时级离线把"用户→命中的 experience/variation/payload 引用"算好写入 KV（Redis 等），fetch 退化为一次毫秒级 KV 点查。
  适用：人群相对稳定、批量为主、首页秒级 SLA 强约束；与 Botim T+1 主路线 + 实时占比小高度契合，实时性弱是代价。

- **方案 C：混合（预计算为主 + 实时兜底 + 边缘/客户端缓存）**
  做法：默认走 B 的预计算 KV；KV miss 或需实时属性时回落 A 实时判定；客户端 SDK 缓存上次 payload，fetch 超时/失败回落缓存或默认内容（D2）。多层降级保命中率与体验。
  适用：绝大多数 Botim 首页场景——既要秒级稳定又要少量实时兜底与高可用。

## 3. 优劣对比表

| 维度 | A 实时命中 | B 预计算 KV | C 混合（预计算+兜底+缓存） |
|---|---|---|---|
| 实现成本 | 中（直接复用 M2，但要扛 QPS） | 中（建离线作业 + KV 写入治理） | 中-高（两条路径 + 降级逻辑 + 缓存契约） |
| 性能·延迟 | 低-中（规则求值难稳定秒级） | 高（KV 点查毫秒级） | 高（主路径毫秒，兜底偶发慢） |
| 可扩展 | 低（QPS 随用户线性涨，扩容贵） | 高（读扩展靠 KV 水平扩） | 高（读扩展 + 实时仅兜底，压力小） |
| 运维 | 中（在线规则引擎热点/限流） | 中（离线作业 + KV 一致性/过期） | 低-中（多层但各层成熟，降级自愈） |
| 对 Botim 适配度 | 低（秒级 SLA 下风险高、实时占比又小） | 中-高（契合 T+1，但纯预计算实时性弱、KV 冷启动差） | 高（秒级稳定 + 少量实时兜底 + 缓存降级，最贴首页） |

## 4. 业界典型做法
- **内容决策 API（Content Decisioning）**：Adobe Target / Optimizely 等"按 key 返回该用户内容/变体"的决策接口，正是 fetch 的对标形态。
- **Feature Store + 在线推理**：离线算特征/人群标签入在线特征存储，请求时低延迟读取——即方案 B 的工业化形态。
- **CDN 边缘缓存 + KV（Redis）查询**：首页这类高 QPS 内容下发普遍用边缘/Redis 做毫秒级 KV 命中 + 缓存降级，印证方案 C。

## 5. AI 新做法
- **个性化推荐（召回 + 排序）**：依用户画像/历史行为对候选内容/variation 做召回+排序智能命中（B5），比静态规则更"千人千面"。
- **多臂老虎机（MAB）选最优 variation**：在 A/B/N variation 间在线探索-利用，自动把流量倾斜到高转化变体，省去人工分流（B3 增强）。
- **生成式内容**：payload 文案/卡片内容由 M6 生成式多语种产出，实现内容侧千人千面。

## 6. 面向 Botim 的推荐选型
**选方案 C：预计算为主 + 实时兜底 + 客户端/边缘缓存降级。** 首页秒级 SLA + 实时活动占比小 + Botim T+1 主路线，决定主路径应是"离线把用户→experience/variation/payload 引用算好写 Redis，fetch 做毫秒级 KV 点查"；仅对需要实时属性或 KV miss 的少量场景回落 M2 规则引擎实时判定，避免在线规则求值扛全量 QPS；客户端 SDK 必须做缓存 + 超时降级（D2/D3），fetch 失败回落上次 payload 或默认卡片保首页体验。命中判定逻辑统一收口 M2 规则引擎（一处建多处用）。AI 个性化推荐（B5）与 MAB 选优作增量后置，先把"对等 fetch + 脱钩"在 Phase 1 打通一个卡片位验证可行性。前置先关 R1（KV schema 归属）、R3（实时性 SLA 档位）、R4（customer_id 跨业务线映射覆盖率）。

# M6 · AI 文案（多语种生成 + 效果闭环）

## 1. 需求与约束回顾
纯增量模块，MoEngage 无对应物。核心是 **多语种一键生成**（A1，印/菲/阿/英）压缩"写文案"瓶颈（row18），本地化非机翻（A2，阿语 RTL），多版本喂 M3 A/B/N（A3），生成可预览可编辑（A4，AI 非黑盒）。通过 **历史文案-效果闭环**（B，join 点击率/转化率/ROI）让 AI 学高转化风格。合规/敏感词初筛（C1）+ Growth 自审（C2）。文案绑定/存储（D）供 M3 编排、M5 payload 调用。闭环可行性取决于 D16/D17 配对数据完整性（R1）。

## 2. 候选技术方案（≥2）

- **方案 A：通用 LLM API + Prompt 工程（零样本/少样本）**
  做法：调用通用大模型 API，用结构化 prompt（活动目标/Offer/人群/语种/品牌语气）+ few-shot 示例直接生成多语种文案，运营预览可编辑。
  适用：起步最快、零训练成本、多语种开箱即用；品牌一致性靠 prompt 约束，质量上限受 prompt 工程与示例质量影响。

- **方案 B：RAG 检索增强（检索历史高转化文案/品牌语料注入）**
  做法：把历史高转化文案 + 品牌语料建向量库，生成时检索 top-k 相关样本注入 prompt（in-context），让产出贴近本品牌已验证的高转化风格。
  适用：已有历史文案-效果配对数据（D16/D17 到位）、要品牌一致性与"学过往高转化"；是 B 组效果闭环的轻量工程实现，无需训练。

- **方案 C：领域微调 / LoRA（多语种 + 品牌语气）**
  做法：用配对样本对开源/可微调模型做 LoRA 微调，固化品牌语气与各语种本地化风格，分语种分别建模（B3）。
  适用：文案量大、品牌语气强约束、追求稳定一致与可控成本（推理便宜）；但数据/训练/评测/迭代成本高，需配对样本充足。

## 3. 优劣对比表

| 维度 | A Prompt 工程 | B RAG 检索增强 | C 微调/LoRA |
|---|---|---|---|
| 实现成本 | 低（接 API + 写 prompt） | 中（建向量库 + 检索链路） | 高（数据治理 + 训练 + 评测迭代） |
| 性能·延迟 | 高（单次 API 调用，快） | 中（多一次检索，仍可接受） | 高（自托管推理快，但前期长） |
| 可扩展 | 中（加语种/场景靠改 prompt） | 高（扩语料即扩能力，热更新） | 中（新风格需重训/再微调） |
| 运维 | 低（托管 API，几乎免运维） | 中（向量库 + 语料更新） | 低-高（模型托管 + 重训管线，重） |
| 对 Botim 适配度 | 高（起步最快、四语种开箱、可编辑） | 高（直接兑现 B 组效果闭环 + 品牌一致） | 中（数据未必齐、ROI 待验证，宜后置） |

## 4. 业界典型做法
- **Jasper / copy.ai 模式**：营销文案生成产品化路径——模板 + brand voice 约束 + 多语种，证明"通用 LLM + prompt/品牌语气约束"足以支撑营销文案场景。
- **Brand Voice 约束**：用品牌语气样本 + 风格指令固定调性，对应 A2 本地化与品牌一致。
- **机器翻译 vs 原生多语种生成**：业界共识是营销文案应"原生多语种生成"（按当地表达习惯）而非英文直译，正对应 A2 非机翻要求。

## 5. AI 新做法
- **效果反馈闭环（bandit / RLHF 选高转化文案）**：把 M4 回流的点击率/转化率作奖励信号，用多臂老虎机/偏好学习在候选文案间选高转化版本（B4 效果回流增量学习）。
- **多语种原生生成 vs 翻译**：直接以目标语种生成并按本地表达习惯适配（A2），优于"英文写好再翻"。
- **合规敏感词初筛**：生成侧做 UAE 合规 + 敏感词初筛（C1）过滤明显违规，再交 Growth 自审（C2）。

## 6. 面向 Botim 的推荐选型
**起步走 Prompt 工程（A），数据到位后叠加 RAG（B）兑现效果闭环，微调（C）后置。** Phase 1 先用通用 LLM API + 结构化 prompt 做"英文 + 1 主力语种"生成 + 可编辑 + 人工把关（A4/C2），不依赖效果闭环即可上线，最快压缩"写文案"瓶颈；待 D16/D17 历史文案-效果配对数据到位（R1 关闭），把历史高转化文案 + 品牌语料建向量库做 RAG，生成时检索注入，低成本实现 B 组"学高转化风格"且保品牌一致；多语种坚持**原生生成而非机翻**（A2，阿语 RTL 适配）。只有当文案量足够大、配对样本充足、品牌语气需强固化时再评估 LoRA 微调，避免过早投入高成本训练管线。效果闭环用 M4 回流数据做 bandit 选优（B4）作增量。合规初筛（C1）按 Growth 给的口径（R2）落地，未定前先做通用敏感词兜底。

## 收口：三模块推荐一览

| 模块 | 推荐主干 | 一句话理由 |
|---|---|---|
| **M4** | 接现成 OLAP 用 `windowFunnel` + 高频漏斗 T+1 预计算；跨产品漏斗待 M8 ID-mapping 打通 | 引擎内置序列算子最优，跨产品依赖 customer_id 跨线打通，先关 ID 前置 |
| **M5** | 预计算为主 + 实时兜底 + 缓存降级（方案 C） | 首页秒级 SLA + 实时占比小 + T+1 主路线，KV 点查毫秒级最稳 |
| **M6** | Prompt 工程起步 → RAG 兑现效果闭环 → 微调后置 | 最快落地、数据到位后保品牌一致与高转化，微调成本高宜后置 |
