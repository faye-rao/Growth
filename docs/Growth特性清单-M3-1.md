## 0. 模块定位
- **优先级**：P0（"我方做的 3 个核心功能"之二，触达之后、衔接圈人，Survey 结论#6 / row76）。
- **基线**：复刻 MoEngage "纯规则引擎 3 步法"的第②③步——②定 content（A/B/N 组 + 版本微调）、③定推送时间/条件（row32）。
- **增量主线**：叠加 **🤖AI 编排**（自然语言描述活动目标→自动生成人群+文案+排期+Flow，survey 明说"可探讨用大模型(GPT)替代编排" row22），兑现"**增量靠 AI 提升活动量/验证效率**"（row6）；并**正面补全 MoEngage 完全空白的跨活动频控/去重/静默时段**（row38/42）。
- **现状事实**：~800 活动/年、≈2–3 条/天（row12）；最常用能力＝活动配置下发到每个用户 + 分群后发推送（row21）；以批量活动为主、部分实时触发（row62）；**无跨活动去重、无每用户每日上限、一天可能收 3 条**（row38/42）；In-App 弹窗可设首次/每页首次/每天首次（row37）；时区统一 Asia/Dubai（UAE）。Flow 在用节点类型/复杂度未知，待 Growth 确认（row35/36）。

## 4. 依赖关系
### 4.1 技术依赖
- **M2 圈人 → 前置 M3**：编排需 M2 圈人结果作为活动人群输入（G2）；无人群则编排无对象。
- **分流器复用 M5/M2**：B2 自动分流复用 M5/M2 规则引擎，不重复造（line72/line160）。
- **M1 触达执行 → 承接 M3**：编排结果交 M1 落地发送（Push/In-App），衔接限速（G3）。

## 5. 前置阻塞与风险
- **R1 频控上限未知** → 每用户每日上限、静默时段需 **Growth 结合 UAE 当地政策与用户疲劳度**确定，否则 E1/E3 无法定参数（row42/47）。
- **R2 实时占比是触发型活动开关** → 若 Growth 反馈实时活动比重高，A3 触发型编排加重、依赖 M2 近实时分群（row62）。
- **R3 Flow 复杂度未知** → 在用节点类型与典型 Flow 分支层数未拿到（row35/36），A5 节点范围与编排引擎复杂度无法精准估，可能需扩展状态机。
- **R4 AI 编排可行性** → F1 自然语言→人群/文案/排期/Flow 端到端可控性待验证；策略：**作为增量并行，可预览可编辑兜底（F2），不作 Phase 1 阻塞**。

## 6. Phase 落地建议
- **Phase 1（W3–W4 MVP）**：先做 **3–5 个高频活动模板（D1/D2）+ A/B/N（B1–B3）+ AI 文案（M6/F3）接入**，跑通一个高频场景（如钱包激活 Push）的完整编排。
- **🤖AI 编排（F1/F2）作为增量并行推进，不作为 Phase 1 阻塞项**（对齐 line187 ④）。
- **频控/去重（E1–E3）可降配后置**（现状本就没有，不影响"不低于现状"目标）；但 **Shadow 期去重中间层（M7/E4）必需**，否则用户被双推、对照失真（line186）。
- **Phase 2+**：补全 Flow 全节点类型（A5，待 row35/36 确认后）、完整频控/去重/静默时段（E1–E3）、AI 编排横向铺开。
- **建议顺序**：先关 row35/36（Flow）、row42/47（频控政策）、row62（实时占比）前置访谈 → MVP 跑通模板+A/B/N+AI文案 → 验证后扩频控与 AI 编排增量。
