# Botim 增长平台 · 全模块技术方案、工作量(人日)与开发周期

> 覆盖两段录屏全部模块：**Segment / Engage(Campaigns/Flows) / Personalize / Analyze / Dashboard**，外加 **Data 清洗 / Reports**。
> 前提：① 工作量以**人日(person-day, 净开发)**计；② OLAP 由数据组定，本文按"需引入标准 OLAP(ClickHouse/Doris/StarRocks)"中性假设，标注"接现成"可省量；③ Analyze/Reports **以效果归因为主**，自助 BI 探索降配后置；④ 数据底座=已有 App SDK 端内打点，**无 email**，时区统一 **Asia/Dubai (UTC+4)**。
> 协同原则：**数据清洗=底座(被全员依赖)**；**Personalize 实时命中复用 Segment 规则引擎**；**Reports 复用 Analyze 归因引擎**；**Dashboard 复用 Analyze 查询层**。严禁各模块各算各口径。

## 1. 数据清洗（底座，最高优先级）

### 技术方案
Kafka 接入 + Schema Registry 事件治理；**ID-Mapping**(无 email→customer_id/手机号主键 + 多端设备图谱)；标准化(去重/迟到纠偏/时区归一 UAE/属性规整)；用户宽表+事件宽表+RFM 基础；**可配置衍生标签框架**(Count/Sum/First-Last/SQL)→标签服务化；DAG 调度 + DQC 质量监控告警。

## 2. Segment（用户分群，核心 P0/P1）

### 技术方案
| 子系统 | 方案 |
|---|---|
| **规则引擎 DSL** | 自定义条件 DSL：事件+频次(atleast/min%/predominantly)+属性条件+时间维度(hour/month)+时间窗+嵌套+排除+OR+in-session；解析器+校验器。 |
| 求值执行器 | 批量跑批(over 宽表/OLAP) 出人群快照；记录 Last Run。 |
| 近实时分群 | 事件触发增量更新人群(呼应 in-session/实时圈人)。⚠️依赖实时流。 |
| RFM 分群 | R/F/M 三事件选择+分箱+Conversion Goal 模板。 |
| File/Import | 名单导入(File Segment)+User Imports/Exports。 |
| **NL2SQL** | 自然语言→规则 DSL(接 LLM + 事件字典语义)。 |
| 分群管理 | 列表/类型过滤/版本/归档/Synced 同步。 |
| 服务化 | 人群结果存储+接口，供 Engage/Personalize 消费。 |
| 前端 | 可视化条件构造器(嵌套/拖拽)+RFM 配置页+列表。 |

## 3. Personalize（千人千面 / Web Experience，核心 P2-1）

### 技术方案（★ 视频实拍的 fetch API 直接复刻）
| 子系统 | 方案 |
|---|---|
| **fetch API** | `POST /experiences/fetch`：鉴权(Basic+APPKEY)+解析 identifiers+experience_key→返 content payload。 |
| 实时命中 | **复用 Segment 规则引擎**按 experience_key 判定 audience 命中。 |
| Variation 分流 | Auto/手动百分比 + 全局对照组扣留。 |

| 客户端集成 | 多端 SDK 示例 + 缓存/降级策略(客户端自渲染)。 |
| 前端 | 三步向导(选人→内容→排期)。 |

## 10. 开发周期（日历）

这是一个**平台级程序(program)**，需多小组并行。以**样例配置**换算（按实调整）：

**样例团队**：后端×4、数据工程×2、前端×4、QA×2 ≈ **12 人**；协作损耗后有效产能 ≈ **8 人日/日**。

### 关键依赖链
- **数据清洗(底座)** 前置于所有分析/圈人/归因。
- **Segment 规则引擎** 前置/共享于 **Personalize 实时命中**。
- **Analyze 归因引擎** 前置/共享于 **Reports**。
- Dashboard 依赖 Analyze 查询层。

### 阶段计划（含重叠并行）

| 阶段 | 内容 | 日历 |
|---|---|---|
| **P0 准备/选型** | OLAP 定型、埋点 schema 冻结、ID-Mapping 方案、归因口径共识、平台框架搭建 | **2 周** |
| **P1 底座** | 数据清洗(宽表/标签/DQC) + 平台通用组件 | **4–5 周** |

## 11. 关键假设、摆动因子与建议

1. **OLAP 选型（最大变量，±15–20 人日 / ±2–4 周）**：优先推数据组拍板。接现成最省。
2. **埋点 schema 稳定性**：事件字典需大改/补埋点→P0 拉长 + 清洗返工。
3. **归因口径共识**：归因窗口/首末触/对照组定义需 Growth 早定，否则 Analyze/Reports/Engage 三处返工。
4. **无 email**：ID-Mapping 以 customer_id/手机号为主键 + 多端打通，是清洗模块重点工作量。
5. **共享组件是省人日关键**：规则引擎(Segment↔Personalize)、归因语义层(Analyze↔Reports↔Engage)、查询层(Analyze↔Dashboard) 必须复用，否则总量会比上表多 15–20%。
6. **Token 红线**：Engage/Personalize 不接管推送 Token，最后一公里走 Botim 接口。
7. 人日为净开发，未含需求评审/长尾运维；已给 15% 缓冲建议。

### 落地建议
- **先打最小闭环**：清洗→单分群→单 experience 下发→单活动→活动报表+归因，跑通 0→1→2/3→4/6 全链路，再横向铺开。
- **面向契约并行**：P0 即冻结"清洗宽表/标签接口契约"与"规则引擎/归因语义层接口"，让各小组用 mock 先行，最大化并行、缩短串行等待。
- **优先级**：P0/P1/P2-1 核心(Segment+Personalize+Engage+清洗) > Analyze/Reports(效果回收) > Dashboard(可选)。
