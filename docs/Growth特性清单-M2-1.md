## 0. 模块定位
- **优先级**：P0（"我方做的 3 个核心功能"之一，触达之后第二优先，Survey 结论#3/#6）。
- **基线**：复刻 MoEngage "纯规则引擎 3 步法"第①步圈人（row32）。
- **增量主线**：叠加 AI（NL2SQL / 智能分群）+ 体验增强，正面解决 Survey 点名的"**很难用**"（row32），兑现"**增量靠 AI**"（row6）。
- **现状事实**：80% 活动只用 5–10 个分群；纯手动规则筛选、非 AI 推荐；T+1 清洗 + 小时级，非瓶颈；无 email、业务线 ID 未打通、无 CDP。

## 2. 🤖 AI 与 ★增强 特性汇总（相对 MoEngage 的差异化）

**🤖 AI 能力（增量主线，对齐 row6 "增量靠 AI"）**
- M2-B1 自然语言圈人 NL2SQL ← **最强亮点，直击"很难用"**
- M2-B3 / B4 NL2SQL 准确率兜底 + 模板优先
- M2-C1/C2/C3/C4 Lookalike / 倾向分群 / AI 分群建议 / 分群效果算法优化

**★ 本次增强（优于 MoEngage 现状）**
- M2-A6 可视化构造器 + 实时人数预估（破"无穷嵌套很难用"）
- M2-A7 兼容 MoEngage 语法查询层（平滑迁移 ~800 活动）
- M2-B2 生成结果可预览可编辑（AI 非黑盒）
- M2-D2 高频 Cohort 模板库（覆盖 80% 活动的 5–10 个分群）
- M2-E2 跨业务线 ID 打通（无 email 前提）
- M2-E3 "已转化不再推"准实时抑制

**一句话定位**：M2 = **复刻 MoEngage 圈人引擎（A1–A5/D/E1/F 基线）+ 兼容层平滑迁移（A7）+ AI 与体验增强（B/C + A6/D2/E2/E3）正面解决"很难用"并兑现"AI 增量"**。

## 5. 前置阻塞与风险
- **R1 数据样本 + 事件 schema 未到位** → A 全组与 E1 无法动工（裴青/数据组）。
- **R2 实时占比是工期开关** → 若 Growth 反馈实时活动 >30%，A8 近实时加重、6 周 MVP 吃紧（row62）。
- **R3 NL2SQL 可行性** → 取决于历史 SQL 复杂度(D7)与重复模板占比(D6)；策略：**先做高频模板覆盖 + 人工兜底，不赌全自动**（B3/B4）。
- **R4 Top Cohort 未知** → D13 未拿到则 D2 模板库与 A 组算子覆盖范围无法精准（Growth）。
- **R5 ID 打通现状未知** → 无 email 前提下，D2 Mapping 覆盖率/准确率决定 E2 难度（数据组）。

## 6. Phase 落地建议
- **Phase 1（W3–W4 MVP）**：圈人=**复用现有规则引擎 + 兼容语法层(A7) + 分群算法(C4)**；NL2SQL 先做**最常用模板 + 兜底(B3/B4)**，不作为阻塞项。
- **Phase 2+**：补全可视化构造器(A6)、Lookalike/倾向分群(C1/C2)、近实时(A8)、模板库(D2) 横向铺开。
- **建议顺序**：先关 D1–D15 前置数据/访谈 → MVP 跑通一个高频场景（如钱包激活 Push）的圈人 → 验证后扩 AI 增量。
