# Growth 技术方案对比 · M1 触达执行 / M2 圈人 / M3 编排

> Botim 自研增长平台（MoEngage 竞品替换）核心三模块技术选型对比
> 配套需求：`Growth特性清单-M1-1.md` / `M2-1.md` / `M3-1.md` / `总览索引.md`
> 贯穿约束：footprint 全量埋点备份已有；数据组 T+1 清洗、MoEngage 侧小时级；**无 email**（主键 customer_id / 手机号）；**OLAP 引擎未定**（数据组拍板）；业务线未打通、无 CDP；~800 活动/年、2–3 条/天、最大百万级/活动；**以批量为主、部分实时**；Push/SMS 走 Botim 自有通道（已收口，MoEngage 无直推权），In-App SDK 自渲染；现状无跨活动去重 / 无频次上限；**增量靠 AI；先复用现有规则引擎 + 兼容层做 6 周 MVP**。

---

## 一、M1 触达执行（Push + In-App 弹窗）

### 1.1 需求与约束回顾
复刻 MoEngage 触达执行：Push/SMS 走 Botim 已收口的自有通道（MoEngage/我方均无三方直推权），In-App 弹窗 SDK 自渲染、不过后端，补全用户级触达日志（前置 M4 漏斗 / M7 Shadow）。约束：单活动最大百万级、批量为主；接口侧限速 + Opt-out 名单过滤为外部依赖；现状无频控/去重（主体在 M3，M1 仅做执行侧接入点）；无 Email，兜底只能在 Push/SMS/In-App 间组织。

### 1.2 候选技术方案

**方案 A — 各渠道独立适配（per-channel 直连）**
- 做法：为 Push、SMS、In-App 各写一套发送逻辑，业务侧直接调对应通道接口（FCM/APNs/Botim SMS 网关/SDK 下发），各自实现重试、回执、限速。
- 适用场景：渠道极少、量级小、无统一频控/兜底诉求的早期阶段；快速打通单一高频场景（如钱包激活 Push）。

**方案 B — 统一触达网关（channel-agnostic gateway，推荐底盘）**
- 做法：对上暴露一个与渠道无关的 `send(customer_id, channel_hint, content, policy)` API；内部 adapter 层把统一消息翻译成各通道协议（Botim Push 接口 / SMS 通道 / In-App 下发）；中间用 **Kafka 做削峰缓冲**（百万级活动入队后匀速消费），统一实现限速令牌桶、指数退避重试、回执/已读回流、Opt-out 前置过滤、执行侧频控接入点（C2）。多渠道兜底降级（A5）在网关编排：Push 不可达→SMS/In-App。
- 适用场景：多渠道、百万级批量、需要统一频控/兜底/回执/可达性过滤的中长期形态——正是 Botim 目标态。

**方案 C — 复用 Botim 已收口接口 + 薄编排层（MVP 务实路线）**
- 做法：不重造网关，直接在 Botim 已收口的 Push/SMS 接口之上包一层薄编排（队列 + 限速对接 + Opt-out 过滤 + 日志埋点），In-App 走现有 SDK 下发协议。adapter/兜底/可达性以 hook 形式预留，后续平滑长成方案 B。
- 适用场景：6 周 MVP，先用最小改动跑通"钱包激活 Push + 触达日志"，规避对 Botim 开放平台接口规格未明（R4）的过度设计。

### 1.3 优劣对比表（高 / 中 / 低）

| 维度 | A 各渠道直连 | B 统一触达网关 | C 复用收口接口 + 薄编排 |
|---|---|---|---|
| 实现成本 | 低（单渠道）/ 中（多渠道重复） | 高 | **低** |
| 性能·延迟 | 中（无削峰，易打爆） | **高**（Kafka 削峰、匀速消费百万级） | 中 |
| 可扩展（加渠道/能力） | **低**（每加一渠道重写） | **高**（加 adapter 即可） | 中（预留 hook，需演进） |
| 运维 | 低（逻辑分散难统一观测） | **高**（统一限速/重试/回执/监控） | 中 |
| 对 Botim 适配度 | 低 | 中（理想态但接口规格未明、易过设计） | **高**（贴合已收口现状 + 6 周窗口） |

### 1.4 业界典型做法
- **统一 Push Gateway / Notification Service**：Uber、LinkedIn、Airbnb 均有 channel-agnostic 通知网关（如 LinkedIn 的 Air Traffic Controller、Uber 的 push platform），上层与渠道解耦、下层 adapter。
- **Kafka 削峰 + 分层限速**：百万级批量入 Kafka topic，消费端按通道配额令牌桶限速，避免 FCM/APNs 侧被限流或自有页面被打爆（对应 C1）。
- **APNs/FCM token 生命周期管理**：失效 token 回收（APNs feedback / FCM unregistered 响应）——这正是"已卸载用户永远收不到"(R1)的工程根因。
- **回执/已读追踪**：delivery receipt + read receipt 回流，做送达率与后续可达性建模的数据源（E1/E2 触达日志）。

### 1.5 AI 新做法
- **送达可达性预测（M1-F2）**：以 footprint 活跃度 + 历史回执 + 设备/平台特征训练模型，对目标人群打"可达概率"分，优先发高可达用户、过滤低活跃（直击"Android 到达率低于 iOS、选到已卸载永远收不到"）。
- **无效用户过滤（M1-F1）**：结合 token 失效信号 + AI 离线/卸载预测，发送前剔除注定收不到的用户，提升有效送达率与通道 ROI。
- **最佳发送时间 STO（Send-Time Optimization）**：按每用户历史打开时间分布预测个体最优发送时刻，错峰发送（业界 Braze/MoEngage STO 同款思路），既提打开率又天然平滑削峰。
- **Next-Best-Channel**：当 Push 低可达时，AI 决策降级到 SMS 还是 In-App（而非固定规则），与 A5 兜底联动。

### 1.6 面向 Botim 的推荐选型
**MVP 走方案 C、架构按方案 B 收口。** 6 周窗口 + Botim 接口已收口 + 限速/Opt-out 规格未明（R4），决定 Phase 1 不重造网关：用薄编排层贴现有 Push/SMS 收口接口跑通钱包激活 Push + 触达日志（A1/B1/C1/D1/E1），但**入队即用 Kafka、adapter 与 policy 钩子按方案 B 形态预留**，避免后续推倒重来。AI 增量（F1/F2 可达性、STO）依赖触达日志（E1/E2）积累，作为 Phase 2 叠加，不阻塞 MVP。统一频控接入点（C2）此处只留执行侧 hook，主体在 M3。

## 二、M2 圈人（规则引擎 + NL2SQL）【重点 · 3 方案】

### 2.1 需求与约束回顾
复刻 MoEngage "纯规则引擎 3 步法"第①步圈人：多条件无穷嵌套 AND/OR/NOT、时间窗/频次算子、排除人群、批量求值刷新到小时级。约束：**80% 活动只用 5–10 个分群**、批量为主、T+1 清洗 + 小时级（非瓶颈）；**OLAP 引擎未定**（数据组拍板）；无 email、业务线 ID 未打通、无 CDP；需兼容 MoEngage 语法层平滑迁移 ~800 活动、复用现有规则引擎不全量重写；增量靠 AI（NL2SQL）。"已转化不再推"是主要实时诉求。

### 2.2 候选技术方案（3 个）

**方案 A — 解释执行 DSL（规则树实时遍历）**
- 做法：把规则定义为 AST/规则树，求值时逐用户遍历规则树判定命中（内存或逐行扫描）。表达力强、支持任意嵌套与复杂算子，规则改了立即生效、无需重新编译下推。
- 适用场景：实时/近实时单用户判定（如"已转化不再推"抑制、触发型活动逐事件判定）、人群规模小、规则极其灵活；**不适合**百万级全量批量扫描（逐行遍历成本高）。

**方案 B — 编译到 SQL（DSL → SQL 下推 OLAP）**
- 做法：DSL/兼容 MoEngage 语法层解析后**编译成 SQL**，下推到数据组的 OLAP 引擎（ClickHouse/Doris/StarRocks 等）在大宽表上执行，结果即人群快照。复用 OLAP 的列存 + 向量化 + 分布式扫描跑百万级。
- 适用场景：批量为主（Botim 现状）、已有/将有 OLAP 大宽表、时间窗与聚合算子多。**强依赖数据组 OLAP 选型落定**。

**方案 C — 预计算 + 倒排 / Bitmap（标签倒排 + RoaringBitmap）**
- 做法：T+1/小时级把用户标签预计算成**标签→用户的倒排索引**，每个标签值对应一个 **RoaringBitmap**（customer_id 映射为整型位）；人群交并差 = bitmap 的 AND/OR/ANDNOT，秒级完成大人群运算；人数预估直接取 bitmap 基数。
- 适用场景：高频复用的 5–10 个固定分群（命中 80% 活动）、需要实时人数预估、大人群交并差频繁；离散标签型条件最优，复杂时间窗/连续聚合算子需配合预计算物化。

### 2.3 优劣对比表（高 / 中 / 低）

| 维度 | A 解释执行 DSL | B 编译到 SQL | C 倒排 + Bitmap |
|---|---|---|---|
| 实现成本 | 中（引擎可复用现有） | 中（解析器 + SQL 模板，复用兼容层） | 高（需建标签预计算 + 索引管线） |
| 性能·延迟（百万批量） | **低**（逐行遍历慢） | 高（OLAP 向量化） | **高**（bitmap 秒级交并差） |
| 性能·延迟（单用户实时） | **高**（树遍历即时） | 低（SQL 起步开销大） | 中（需查多个 bitmap） |
| 可扩展（算子表达力） | **高**（任意嵌套/自定义算子） | 高（SQL 表达力强） | 中（离散标签强、连续/时间窗弱） |
| 运维 | 中 | **高**（借数据组 OLAP，少自维护） | 低（自维护索引 + 一致性/更新） |
| 对 Botim 适配度 | 中（适合 E3 实时抑制 + 触发型） | **高（若 OLAP 落定）**（批量为主 + 复用兼容层） | 中（适合高频模板提速，前期重） |

### 2.4 业界典型做法
- **规则编译 SQL + OLAP 大宽表**：Segment / Amplitude / mParticle 的 audience/segment engine 多走"规则 → 查询下推列存"，ClickHouse / Apache Doris / StarRocks 是常见执行底座；用户行为打成大宽表跑批。
- **RoaringBitmap 人群圈选**：阿里达摩盘 / 神策 / GrowingIO / 腾讯标签平台普遍用 RoaringBitmap 做亿级人群交并差与实时人数预估，是标签平台事实标准（Druid、Doris 内部 bitmap 聚合同源）。
- **CDP Segment Engine**：批量 segment（T+1/小时级物化）+ 实时 segment（流式更新）双轨，正对应 Botim "批量为主 + 已转化实时抑制"。
- **解释执行 DSL**：Drools / 自研规则树用于实时单用户判定与触发型场景。

### 2.5 AI 新做法
- **NL2SQL 三条路线对比**：
  1. **模板 / 槽位填充**：预置高频取数模板（结构同、参数异），NL 只填槽位。准确率高、可控、零幻觉，但覆盖窄。→ 对应 B4 模板覆盖优先、D2 高频模板库。
  2. **RAG + schema-linking + LLM**：把表/字段/标签字典 + 历史 SQL 检索进上下文，LLM 生成 SQL。覆盖广、灵活，但有幻觉风险、依赖 schema 质量与标签字典完整度。
  3. **领域微调 LLM**：用 Botim 历史取数 NL-SQL 对微调专用模型。准确率天花板高，但需足量标注样本、迭代成本高，6 周内不现实。
- **准确率兜底（B2/B3）**：生成 SQL/DSL **透明可预览可编辑**（AI 非黑盒）；高频模板命中直出，**置信度提示**，长尾/低置信转人工或转可视化构造器（A6）。
- **Lookalike（C1）**：种子人群 → 用户向量相似检索（embedding + ANN）或正负样本分类模型扩展相似人群。
- **倾向分群（C2）**：流失/转化/激活倾向打分（GBDT/逻辑回归），把"纯规则筛选"升级为"按概率分群"。

### 2.6 面向 Botim 的推荐选型
**分支结论，取决于数据组 OLAP 是否落定：**
- **若 OLAP 引擎已定/将定（首选）→ 方案 B 为主干**：兼容 MoEngage 语法层（A7）解析后编译 SQL 下推 OLAP，复用现有规则引擎不重写、批量为主天然契合、运维借数据组少自维护，6 周 MVP 最稳。
- **若 OLAP 短期无定论 → 方案 C 兜底**：先用倒排 + RoaringBitmap 把高频 5–10 个分群（覆盖 80% 活动，D2）预计算成 bitmap，秒级交并差 + 实时人数预估（满足 A6），不等 OLAP 也能跑通 MVP。
- **方案 A 做"实时补位"而非主干**：解释执行 DSL 专供"已转化不再推"准实时抑制（E3）与触发型活动逐事件判定（A8），与 B/C 的批量主干互补。

NL2SQL 走 **路线 1 + 路线 2 组合**：先固化高频模板（路线 1，保准确率与 6 周可交付），长尾用 RAG + schema-linking（路线 2）+ 可预览可编辑兜底；不赌全自动、不上微调（R3）。AI 增量（Lookalike/倾向分群）作为 Phase 2 叠加。

## 三、M3 编排（A/B/N）

### 3.1 需求与约束回顾
复刻 MoEngage 3 步法第②③步：定 content（A/B/N 多组 + 版本微调）、定推送时间/触发条件；活动生命周期状态机；Flow 节点（延时/分支/A·B/等待事件/webhook，复杂度待 Growth 确认 R3）。约束：~800 活动/年、2–3 条/天、**批量为主、部分实时触发**（如"开户后 10 分钟推"）；统一 Asia/Dubai 时区；**填补 MoEngage 完全空白的跨活动频控/去重/静默时段**（现状一天可能收 3 条）；分流器复用 M2/M5 规则引擎；AI 编排（GPT 替代编排）为最大亮点。

### 3.2 候选技术方案

**方案 A — 工作流 / 状态机引擎（Temporal / Cadence / 自研状态机 + Flink CEP）**
- 做法：用持久化工作流引擎（Temporal/Cadence）或自研状态机驱动多步旅程，原生支持"延时/等待事件/分支/超时"等长周期节点；实时触发用 **Flink CEP** 做事件模式匹配（如"开户后 10 分钟未充值则推"）。Flow 即工作流定义，状态可恢复、可观测。
- 适用场景：多步触发型旅程（welcome series、流失挽回 flow）、需要"等事件 + 延时 + 条件分支"的长生命周期编排、实时触发占比高时。

**方案 B — 规则 + 批量调度（DAG / 定时跑批，轻量）**
- 做法：活动 = 一份配置（人群 + content + 排期 + A/B/N 分流比例），用定时调度（类 Airflow/Quartz/cron + DAG）按排期跑批：到点取 M2 人群快照 → 分流 → 交 M1 发送。状态机退化为活动级生命周期（草稿/发布/运行/暂停/结束），无需逐用户长周期工作流。
- 适用场景：批量为主、活动多为"圈人 → 一次性/周期性群发"（Botim 现状 2–3 条/天）、Flow 分支浅；实现轻、运维简单、6 周可落。

### 3.3 优劣对比表（高 / 中 / 低）

| 维度 | A 工作流/状态机引擎 + CEP | B 规则 + 批量调度 |
|---|---|---|
| 实现成本 | 高（引入 Temporal/Flink、学习与运维重） | **低**（调度 + 配置驱动，复用 M2/M1） |
| 性能·延迟（实时触发） | **高**（CEP 秒级事件触发） | 低（跑批粒度，难做秒级触发） |
| 性能·延迟（批量群发） | 中（工作流逐实例开销） | **高**（批量跑批匀速下发） |
| 可扩展（复杂 Flow） | **高**（任意多步/等待/分支） | 中（深 Flow 需扩展状态机） |
| 运维 | 低（多一套有状态分布式系统） | **高**（无额外重组件） |
| 对 Botim 适配度 | 中（实时占比小则杀鸡用牛刀） | **高**（批量为主现状最贴合 6 周 MVP） |

### 3.4 业界典型做法
- **Temporal / Cadence**：Uber（Cadence 发源）、Netflix、Datadog 用其编排长周期、可恢复的多步流程，营销 journey 引擎（Braze Canvas、MoEngage Flows、Iterable）本质都是状态机 + 等待节点。
- **Airflow / DAG 调度**：批量营销活动按 DAG 定时跑批，圈人 → 分流 → 下发是典型 pipeline。
- **Flink CEP / 事件驱动 streaming**：实时触发型旅程（"事件 A 后 N 分钟未发生 B 则触发"）的标准做法，Kafka + Flink CEP 组合。
- **消息编排 / 频控中台**：跨活动频次上限、去重、静默时段（Quiet Hours）通常落在统一发送决策层（如 Braze 的 frequency capping），是 Botim 要补的空白。

### 3.5 AI 新做法
- **AI 编排（M3-F1，最大亮点）**：自然语言描述活动目标 → LLM 自动生成"人群（调 M2 NL2SQL）+ 文案（调 M6）+ 排期 + Flow 草稿"，对应 survey "可探讨用 GPT 替代编排"。结果**可预览可编辑**（F2），AI 非黑盒。
- **智能流量分配（多臂老虎机 bandit）**：用 Thompson Sampling / UCB 的 **contextual bandit** 替代固定比例 A/B/N——动态把流量向胜出版本倾斜，减少劣质版本曝光损失，比固定分流 + 事后显著性检验（B3）更省样本、更快收敛。
- **频控/去重策略优化**：AI 学习个体疲劳度，动态决定每用户每日上限与静默时段（而非全局拍一个固定值），优化"触达量 vs 疲劳/退订"的平衡（E1/E3）。

### 3.6 面向 Botim 的推荐选型
**主干走方案 B、触发型用 CEP 补、AI 编排并行。** Botim 批量为主（2–3 条/天）+ 6 周窗口 + 分流器复用 M2/M5，决定主干用**规则 + 批量调度（方案 B）**：活动配置驱动、到点跑批、A/B/N 固定比例分流 + 事后显著性检验（B3），轻量可落。**触发型活动（如开户后 10 分钟推，占比小）用 Flink CEP 单点补位**，而非为此引入全套 Temporal——除非 Growth 反馈实时占比 >30%（R2）才升级方案 A。跨活动频控/去重/静默时段（E1–E3）作为统一发送决策层补全 MoEngage 空白，但**降配后置**（现状本就没有，不影响"不低于现状"）；**Shadow 期去重中间层（E4/M7）为硬需求必须先做**，防双发污染对照。AI 编排（F1/F2）与 bandit 智能分流作为 Phase 2 增量并行，可预览可编辑兜底，不阻塞 Phase 1。

## 四、三模块推荐选型速览

| 模块 | 主干推荐 | 关键补位 | 触发条件/分支 |
|---|---|---|---|
| **M1 触达** | MVP 方案 C（复用收口接口 + 薄编排），架构按 B（统一网关）收口 | Kafka 削峰 + adapter/policy 钩子预留；AI 可达性/STO 后置 | 接口规格明朗后长成方案 B |
