# M7 · Shadow 验证框架（替换验收命门）

## 1. 需求与约束回顾
Shadow 是"敢替换 MoEngage"的退出条件：对同一用户群切 5% 流量入新系统、余量仍走 MoEngage，2 周内产出"新系统不显著低于 MoEngage"的统计结论（M7-A3 / C1 / C2）。现状无跨活动去重，新旧并行将放大双发问题，**去重中间层是硬需求**（M7-B1）。MoEngage 触达流水接入方式 / 延迟待厂商确认（M7-D1）。

## 2. 候选技术方案（≥2）

### 方案 A：在线流量分流对照（真实并行 A/B + 去重中间层）
- **做法**：复用 M2 规则引擎，对目标人群做确定性哈希切流（`hash(customer_id) % 100 < 5` 入新系统），余量走 MoEngage。两路触达前置一个**去重/幂等中间层**（跨系统单用户触达账本，M7-B2），同一用户在观测窗内只被一路命中。报告侧复用 M4 归因口径，活动发出即 ready、随观测周期自动跑显著性检验。
- **适用场景**：高频、量大、需真实环境验收的场景（如钱包激活 Push）；要求"线上真实表现不低于 MoEngage"的硬验收。这是 Botim 验收命门的主路径。

### 方案 B：离线回放 / 影子对照（历史日志回放比对）
- **做法**：不动正式流量。取历史触达 / 转化日志，用新系统的规则引擎 + 编排"重放"同一批用户，比对新旧两套系统在相同输入下的**决策一致性**（圈人命中、分流、频控判定）。差异点离线归因。
- **适用场景**：上线前的回归 / 冒烟，验证新系统逻辑等价；低频或不便切线上流量的场景；作为方案 A 的前置 sanity check 与补充验证。**非真实投放环境**，无法替代线上效果验收。

## 3. 优劣对比表

| 维度 | 方案 A 在线分流对照 | 方案 B 离线回放对照 |
|---|---|---|
| 实现成本 | 中（去重中间层 + 切流复用 M2，约 23 人日含报告） | 低（复用日志 + 引擎重放） |
| 性能 / 延迟 | 中（实时切流 + 去重需在触达链路前置，毫秒级开销） | 高（离线批，无线上延迟压力） |
| 可扩展 | 高（切流比例 / 场景可配，沿用即扩） | 中（受历史日志覆盖度限制） |
| 运维 | 中（需保障去重中间层不漏不重、双发监控） | 低（离线任务，失败可重跑） |
| 对 Botim 适配度 | 高（验收要求"线上不低于 MoEngage"，唯此可证；日志已到用户级、规则引擎可复用） | 中（只能证"逻辑等价"，证不了线上效果） |
| 统计可信度 | 高（真实并行 A/B，可做显著性检验） | 低（无对照投放，仅决策 diff） |

## 4. 业界典型做法
- **A/B 实验平台**：随机分流 + 显著性检验（如 Optimizely、内部实验平台），是在线对照的标准范式。
- **CUPED（方差削减）**：用实验前协变量削减指标方差，在 5% 小流量、2 周短周期下显著提升检验灵敏度——直接契合 Botim "样本小、周期短"。
- **实验配置中心 / Feature Flag**：分流规则、切流比例集中配置（如 LaunchDarkly 式），M7 可由 M2 规则引擎承担。
- **去重 / 幂等中间层**：消息系统的去重投递（如基于 idempotency key 的去重表 / 布隆过滤器 + Redis 滑窗），正是 M7-B1 的工程原型。

## 5. AI 新做法
- **Uplift modeling（增益建模）**：估计"因被新系统触达而额外转化"的增量，而非简单组间均值差，能在小样本下更准识别真实增益人群。
- **DID（双重差分）/ Synthetic Control（合成控制）**：当随机化不完美或存在系统性差异时，用对照构造反事实基线，提升结论稳健性——适合切流不能完全随机时的兜底。
- **序贯检验（Sequential testing，如 mSPRT / always-valid p-values）**：允许边观测边检验、达到显著即自动早停，**直接缩短 2 周观测周期**、降低 peeking 偏差，与 M7-C3"发出即 ready、自动更新"天然契合。

## 6. 面向 Botim 的推荐选型
**以方案 A 在线分流对照为主、方案 B 离线回放做上线前补充验证。** 验收命门要求证明"线上不显著低于 MoEngage"，只有真实并行 A/B 能给出可信结论；去重中间层（M7-B1/B2）作为硬需求随方案 A 一并落地。统计侧引入 **CUPED 削减方差 + 序贯检验自动早停**，在 5% 小流量、2 周窗口内尽早出可信结论；Uplift / 合成控制作为切流非理想时的稳健性兜底，不作为 MVP 必选。离线回放（B）在切流上线前跑一轮决策等价性回归，降低"新系统逻辑跑偏"风险，二者互补而非二选一。

# M8 · 数据底座（我方部分：接入 + 消费 + 补缺 + 服务化）

## 1. 需求与约束回顾
M8 是 M2 / M4 / M9 / M7 的总前置底座，但**不重建数仓**：T+1 清洗主体归数据组，我方只做"接入 footprint 全量备份 + 消费 ID-Mapping/标签 + 补齐触达/转化日志 + 圈人/漏斗宽表 + 轻 DQC + 服务化"。约束：无 email（主键 customer_id/手机号）、无 CDP、OLAP 引擎未定、批为主、实时诉求主要就为"已转化不再推"（M8-F1）。

## 2. 候选技术方案（≥2）

### 方案 A：接现成 OLAP 直查 + 建消费宽表（最省）
- **做法**：直接复用数据组提供的 OLAP 引擎与 T+1 清洗结果，我方只建**消费侧宽表 / 标签视图**（圈人宽表 M8-D1、漏斗宽表 M8-D2、触达/转化日志宽表 M8-C1/C2），footprint 全量备份接入即用、无需重新埋点（M8-A4）。ID 打通消费数据组的 Mapping 表（确定性匹配，customer_id/手机号主键），不自建映射。
- **适用场景**：批为主、实时占比小、组织上数据组已承担清洗的现状。最快打地基、最低运维。

### 方案 B：自建轻量实时数仓层（Kafka + Flink + OLAP）
- **做法**：在 T+1 批之外，订阅 footprint 的 Kafka 事件流（M8-A5），用 Flink 做流批一体处理，落 ClickHouse/Doris 类 OLAP，支撑触发型 / 准实时场景（"已转化不再推"抑制层 M8-F1）。ID 打通在确定性匹配之外，对未覆盖业务线用概率/图匹配（实体解析）补 Mapping。
- **适用场景**：实时活动占比高（>30%）、触发型营销多、准实时抑制需求强且批次降配不可接受时。

## 3. 优劣对比表

| 维度 | 方案 A 接现成 OLAP + 宽表 | 方案 B 自建轻量实时数仓 |
|---|---|---|
| 实现成本 | 低（约 26 人日，主体复用数据组） | 高（Kafka+Flink+OLAP 自建运维一整套） |
| 性能 / 延迟 | 中（T+1 为主，满足批量场景） | 高（准实时秒级，支撑触发型） |
| 可扩展 | 中（受数据组引擎能力约束） | 高（自有流批层可任意扩） |
| 运维 | 低（不持有重型组件） | 高（Flink 作业 / 流稳定性 / 反压都要扛） |
| 对 Botim 适配度 | 高（批为主、数据组已清洗、OLAP 未定→不绑死） | 中（实时占比小则重型投入回报低） |
| 上线风险 | 低（无回写无下游，替换无中断 M8-F3） | 中（新增实时链路引入新故障面） |

## 4. 业界典型做法
- **Lakehouse**（Delta Lake / Iceberg / Hudi）：湖仓一体，存算分离，契合"复用底层数据、不重建数仓"。
- **CDP**：客户数据平台，但 Botim 无 CDP 且业务线未打通 → 不强上 CDP，仅消费数据组 Mapping。
- **ID-Mapping / 实体解析**：deterministic（确定性，靠强标识 customer_id/手机号）vs probabilistic（概率匹配/图算法）；无 email 场景下确定性为主、概率为补。
- **实时数仓**：Flink + ClickHouse/Doris 是行业准实时标准栈（方案 B 的原型）。
- **Feature Store**：统一离线/在线特征供数（如 Feast），可作为圈人宽表服务化的演进方向，非 MVP 必选。

## 5. AI 新做法
- **实体解析 / ID 打通（图算法 + 概率匹配）**：对数据组 Mapping 未覆盖的业务线，用图聚类 / 概率匹配补 mapping，提升跨产品漏斗可达性——仅作为确定性匹配的补缺，不替代主路径。
- **数据质量 AI 异常检测（DQC）**：在轻量 DQC（M8-E3）上叠加无监督异常检测，自动发现宽表空值率突增、口径漂移、覆盖率掉点，替代人工规则巡检。

## 6. 面向 Botim 的推荐选型
**主推方案 A：接现成 OLAP + 复用 footprint 全量备份 + 建消费宽表，ID 打通以确定性匹配消费数据组 Mapping 为主。** 现状批为主、数据组已承担清洗、OLAP 引擎未定，自建重型实时数仓投入大而回报低。实时只在唯一刚需"已转化不再推"上做**轻量通道**——优先 Kafka 订阅（M8-A5）喂一个轻抑制层（M8-F1），若事件流不稳就降配为更短批次，而非整套 Flink 数仓。换言之：**触发型需求小则不急自建实时数仓**，等实时活动占比真的起来（>30%）再演进到方案 B。概率/图匹配与 AI DQC 作为补缺增量，按 Mapping 覆盖率缺口逐步引入。

# M9 · 行为分析（降配；克制范围）

## 1. 需求与约束回顾
M9 刻意降配（P2）：**不做全量 BI**，只搬 MoEngage 上"真有人看"的 5–10 张报表/漏斗且数字对得上（M9-A1），叠加 AI 数据分析自动化（活动后自动复盘 M9-B1 / 异常归因 M9-B2）。硬约束：Dashboard 归数据组重建、产品侧已有 Amplitude（"花了两份钱"）→ **必须主动划界避免重复**（M9-A5）；口径复用 M4 归因，跨产品漏斗已并入 M4 不重复。

## 2. 候选技术方案（≥2）

### 方案 A：复用 OLAP + 轻 BI 直接 SQL 报表（嵌入式）
- **做法**：直接在数据组 OLAP 上用轻 BI 工具（Superset/Metabase）写 5–10 张报表的 SQL，嵌入式集成到增长平台。口径直接引用 M4 归因语义。
- **适用场景**：报表数量少（5–10 张）、口径已统一、要求最快交付、克制范围。

### 方案 B：预计算指标层 + 轻看板（Metrics/Semantic Layer 统一口径）
- **做法**：在报表之上建一层**指标层 / 语义层**（如 dbt metrics、Cube），把"查看→点击→转化"等口径定义一次、多处复用，预计算后供轻看板与 NL 问数消费。
- **适用场景**：口径需跨报表/跨人统一、未来要接 NL2SQL 自助问数、担心口径分裂时。

## 3. 优劣对比表

| 维度 | 方案 A 轻 BI 直查 SQL | 方案 B 指标层 + 轻看板 |
|---|---|---|
| 实现成本 | 低（直接写 SQL 嵌入） | 中（多建一层语义层 + 预计算） |
| 性能 / 延迟 | 中（直查 OLAP，大查询慢） | 高（预计算，看板响应快） |
| 可扩展 | 低（报表多了 SQL 散落、口径易漂） | 高（口径集中定义，加报表只引用） |
| 运维 | 低（无额外组件） | 中（维护指标层 + 物化任务） |
| 对 Botim 适配度 | 高（仅 5–10 张、口径已统一、要快） | 中（克制范围下略重，但利于口径统一与 NL 问数） |
| 口径一致性 | 中（依赖人工自律对齐 M4） | 高（口径单点定义，天然一致） |

## 4. 业界典型做法
- **Superset / Metabase / Tableau**：开源/商业 BI，嵌入式分析的主流选择，方案 A 直接采用。
- **嵌入式分析（Embedded Analytics）**：把报表嵌进业务系统而非独立 BI 门户，契合"集成进增长平台、不做独立 Dashboard"。
- **Metrics Layer / Semantic Layer**（dbt metrics、Cube）：口径单点定义、跨工具复用，是方案 B 的业界原型，也是防口径分裂（总览 R4）的标准解。

## 5. AI 新做法
- **自动洞察 / 叙事 BI（auto-insights / narrative BI）**：活动后自动生成文字版复盘洞察（"转化环比 +X%，主因 offer A"），兑现 M9-B1。
- **NL 问数（text-to-SQL）**：自然语言自助取数（M9-B3），降低取数门槛，与数据组重看板划界。
- **异常归因**：自动识别效果异常并按 offer/文案/时机维度归因（M9-B2），自动定位"为什么好/为什么差"。

## 6. 面向 Botim 的推荐选型
**克制为先：以方案 A 轻 BI 直查为底，叠加一层薄指标层统一口径（取方案 B 的语义层、不取重看板）。** 仅 5–10 张报表、口径已基本统一、要求快交付，全套指标层偏重；但口径分裂是全公司风险（总览 R4），故把"查看→点击→转化"等核心口径在薄语义层单点定义、直接引用 M4 归因，避免 SQL 散落漂移。**严守边界**：Dashboard/全量 BI 交数据组、通用 BI 交 Amplitude，M9 只做"真有人看的报表 + AI 自动复盘/异常归因/NL 问数"这一差异化增量，**绝不重复 Amplitude**。落地前先关 D25（真看报表清单）/D26（内部指标消费方）/D27（BI 工具栈），并排查 RFM/churn/engagement 是否有人用（M9-C1），若有则先在 M2/M8 补齐再停用。
