## 一、项目概述

为 Botim（迪拜，UAE 上线，目标用户 ≈ 阿联酋人口 1/4 ≈ 250 万）自研一套用户增长平台，替换竞品 MoEngage。我负责从**竞品调研 → 需求澄清 → 方案设计 → 编码落地 → 验证 → 交接**的全流程驱动。最终把 survey 圈定的 **9 个模块（M1–M9）全部建成可运行、可测试的 MVP**，按功能独立性拆为 **7 个服务 + 1 个 API 网关**，接入 CI，并产出完整的需求/方案/对比/交接文档体系。

**工作方法**：竞品录屏逐帧拆解 + survey 访谈结论驱动范围 → 先出特性清单与技术方案（含业界做法与 AI 增量）→ 以 TDD（测试用例先行）+ 独立 Code Review + 功能验证 的纪律逐模块落地 → 契约驱动并行开发提速 → 每模块语义化提交到 GitHub。

## 二、工作过程（9 个阶段）

### 阶段 1 · 环境准备与竞品账号接入
- **目标**：搭好竞品体验/抓取环境，进入 MoEngage 实际产品。
- **工作**：配置 Playwright MCP；登录 MoEngage 控制台（出于安全，凭据由我本人输入、2FA 验证码由我处理）；明确登录与排期等口径**统一使用 UAE 时区（Asia/Dubai, UTC+4）**。
- **关键决策**：凭据不写入任何文件/不交给自动化（安全红线）；时区基线定为 UAE（后续贯穿排期/归因/报表）。
- **产出**：可用的竞品体验环境。

### 阶段 2 · 竞品视频拆解与特性清单
- **目标**：从 2 段 MoEngage 录屏（6'33" 导览 + 4'03" 千人千面实操）吃透特性。
- **工作**：抽帧逐屏分析，按**前端/后端/数据**三层拆解；再按 **Segment / Campaigns / Dashboard / Analyze / Personalize** 等菜单维度组织特性清单。识别出最关键的后端契约 `POST /v1/experiences/fetch`（千人千面"借下发、客户端自渲染"）。
- **关键决策**：确认"首页千人千面 = 自有规则分组 + 仅借下发"路径可自建（风险最低）。
- **产出**：`MoEngage视频特性拆解_前端后端数据.md`、`MoEngage特性清单_按菜单维度.md`。

### 阶段 3 · 结合 Survey 重新厘定范围
- **目标**：用真实访谈结论（`用增问题survey-updated v3.xlsx`，三 sheet）校正"照搬竞品"的范围。
- **工作**：读 survey/Plan/数据分析专项，重定 scope —— 明确 **我方只做 3 核心（圈人/编排/漏斗追踪）+ 触达最高优先**，**Dashboard/重 BI 不做**（数据组+Amplitude 已覆盖），增量靠 AI；梳理模块、依赖关系、工作量、周期、组织阻塞。
- **关键决策**：砍掉 Dashboard/全量 BI，把 Analyze/Reports 降配并入漏斗追踪；确立"6 周 MVP + Shadow 验收"的务实路线。
- **产出**：`Botim增长平台_基于Survey的重新分析.md`。

### 阶段 4 · 特性清单精修与技术方案
- **目标**：把模块需求做成可交接的正式清单 + 可决策的技术方案。
- **工作**：为 M1–M9 各出**正式特性清单**（`Growth特性清单-M*-1.md`，标注【复刻】/★增强/🤖AI + survey 行号溯源 + 交叉检查补全 + 工作量/依赖/风险）；总览索引 + 跨模块依赖图 + AI 亮点地图；为每模块出**≥2 个技术方案对比 + 业界典型做法 + AI 新做法 + 面向 Botim 的选型**；并把清单与技术方案**翻译为英文**供跨团队使用。
- **关键决策**：确立"复刻保不低于现状、AI 做增量"的产品叙事；明确 OLAP 选型为多模块共同前置（待数据组拍板）。
- **产出**：9 份中文清单 + 总览索引 + 3 份技术方案（中/英）+ 9 份英文清单。

### 阶段 5 · M2 落地（首个端到端工程闭环）
- **目标**：用"测试用例→开发→Code Review→功能验证→提交 GitHub"的完整工程纪律落地圈人引擎。
- **工作**：TDD 设计测试用例 → 实现规则引擎 DSL/解析/求值/编译 SQL/人数预估 → 独立 Code Review（修复 SQL 括号、坏 ts 等）→ 全量验证 → 提交并推送到 `faye-rao/Growth`。后续按 **UAE ≈250 万用户**规模决策，增量补 **RoaringBitmap 人群引擎**（秒级交并差）+ NL2SQL + 模板库 + REST API。
- **关键决策**：基于用户规模选 Bitmap 方案 C；NL2SQL 先做确定性模板 + 兜底（不赌全自动）。
- **产出**：`cohort_engine` 模块（多文件）+ 95 测试 + CI 雏形。

### 阶段 6 · CI + M1/M3/M4 落地
- **目标**：补 CI；并行落地触达/编排/漏斗。
- **工作**：补 GitHub Actions CI（py3.10–3.12）；建**共享契约 `growth_common`**（统一触达日志 schema、网关协议、确定性分桶）让模块**面向契约并行开发**；并行落地 M1 触达执行、M3 编排、M4 漏斗；独立 Code Review 发现并修复 **M3 账目不守恒 bug**（网关抑制发送时计数遗漏）。
- **关键决策**：契约驱动并行；以共享契约消解模块耦合。
- **产出**：M1/M3/M4 模块 + CI + 测试报告。

### 阶段 7 · M5/M7/M8/M9 落地 + 端到端集成
- **目标**：补齐千人千面、Shadow 验证、数据底座、行为分析，并串成端到端。
- **工作**：落地 M5（对等 fetch + 控制组）、M7（切流 + 去重防双发 + **CI 非劣检验**，Code Review 修正了非劣统计口径）、M8（接入/ID-mapping/宽表/DQC/抑制，修复 dedup 误并 bug）、M9（报表 + 自动洞察 + 自建 RFM/churn/engagement）；产出端到端 demo + 集成测试。
- **关键决策**：M7 用置信区间非劣检验替代简单显著性；M8 dedup 以 event_id 为权威避免误并真实事件。
- **产出**：M5/M7/M8/M9 模块 + e2e demo + 集成测试。

### 阶段 8 · M6 + 服务化拆分 + API 网关 + 架构总览
- **目标**：补 AI 文案；把平台按功能独立性服务化。
- **工作**：落地 M6（多语种文案 + 合规初筛，Code Review 修复"免责声明被截断"合规 bug）；将 9 模块**按功能独立性拆为 7 个独立服务**（非单体）+ 一个**只做路由/鉴权/限流的 API 网关**；产出架构总览。
- **关键决策**：千人千面/触达/分析等按延迟与扩展画像独立成服务；网关不含业务逻辑、生产用反向代理。
- **产出**：`copywriting` 模块 + `src/services/`（7 服务）+ `src/api_gateway.py` + `ARCHITECTURE.md`。

### 阶段 9 · 归档与交接
- **目标**：沉淀需求与评估，便于交接。
- **工作**：记录全部需求 prompt；**逐文件审计代码 vs 特性清单/技术方案**产出实现对比报告（含完整度 %）；整理交接清单与本工作报告。
- **产出**：`Growth-requirement-prompt.md`、`Growth-实现对比报告.md`、`Growth-交接清单.md`、`Growth-工作报告.md`。

## 三、成果总结（量化）

| 维度 | 成果 |
|---|---|
| 业务模块 | **M1–M9 全部落地**（可运行 MVP） |
| 服务化 | 7 独立服务 + 1 API 网关 + 共享契约 |

## 五、风险与依赖
- **依赖未关闭**：OLAP 选型、数据样本、报表/Cohort 清单、MoEngage 流水等仍多为"待确认"，是估算 ±30% 的根源——开工前必须先关闭。
- **勿过度信任 MVP**：当前无持久化/真实数据源/真 LLM，不可直接对真实流量。
- **数字可信是替换前提**：M4/M9 报表须与旧系统双跑对账，运营才会信任。
- **口径未统一**：转化/活跃/留存无全公司定义，归因须先对齐再开发。
- **Shadow 双发**：上真实 Shadow 前，M7 去重中间层必须接入两套真实发送通道。
