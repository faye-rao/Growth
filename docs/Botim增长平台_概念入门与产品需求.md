## 0. 先理解这门生意：用增是一条"循环流水线"

"用户增长（用增 / Growth）"团队每天在干的事，可以抽象成一条**闭环流水线**，正好就是 As-Is 流程图里的五个环节：

```
① 埋点采集  →  ② 用户分群  →  ③ Campaign 编排  →  ④ 触达用户  →  ⑤ 效果回收分析
   (收数据)      (切人群)        (设计活动)          (发消息)        (看结果)
                                                                        │
                              └──────────── 拿结论回去优化，再循环 ──────────┘
```

**MoEngage 是什么？** 它是一个"营销自动化（Marketing Automation）平台"，把上面 ②~⑤ 这四环打包成一个可视化工具卖给你。Botim 的增长团队（迪拜，约 6~8 人，负责人 Radhika）每天就在 MoEngage 上跑活动。

**我们要做什么？** 资料里反复出现一句关键结论：MoEngage 在 Botim 其实只是个"**下发/触达通道**"——分群规则、首页页面、数据定义全是 Botim 自己做的，埋点数据 Botim 自有平台还留了一份全量备份。所以**真正要替换的不是一个庞然大物，而是这条流水线的中段**。我方明确只需做 3 个核心功能（见第 7 章），其余（如数据看板）由 Botim 数据组自行重建。

下面逐环讲概念。每一环都按 **「是什么 → 打个比方 → Botim 现状 → 我们要做什么」** 来写。

## 1. 埋点（Event Tracking）—— 一切的原材料

### 是什么
**埋点**就是在 App 里"埋"下一个个传感器，记录用户做了什么。用户每点一次按钮、打开一个页面、完成一笔转账，都会产生一条"事件（event）"日志，比如：

```
user_123  在  2026-06-01 14:03  触发了  "完成KYC实名认证"  事件
```

这些原始事件经过清洗、汇总，就能算出"用户画像 / 标签（User Attribute / Tag）"，比如"是否KYC用户""上次转账时间""钱包余额"。

> **打个比方**：埋点 = 超市的收银小票。每一笔记录单看没意义，但攒起来就知道"这个顾客每周三买牛奶、从不买酒"，这就是画像。

### Botim 现状（As-Is） · 🟢 不回写为事实 + 🟡 看哪些报表待 Growth · 🟢 架构事实为主 + 🟡 送达率数字待 Growth · 🟢 无频控为事实 + 🟡 编排/实时占比待 Growth · 🟢 架构事实 + 🟡 常用分群待 Growth · 🟢 架构事实为主
- App 事件**双写**：同时写入 MoEngage 和 Botim 自有埋点平台（叫 `footprint`）。当年接入时就预判 MoEngage 会被替换，所以**自己留了全量备份**——这是替换可行性高的关键证据。
- 数据组（马老板）做 **T+1 清洗**（今天洗昨天的数据），清洗后打上用户标签，再喂给 MoEngage。
- 重要现状：footprint 备份目前**几乎没人看**（大家都在 MoEngage / OnePage 上看）。
- Botim **没有 CDP**（见第 9 章名词解释），各业务线数据**未打通**。

### 我们要做什么
- **数据自主可控**：埋点 schema 和 event 文档要拿到手（找裴青，或直接从 footprint 经数据组拉——比文档更准）。这是整个平台的地基。
- 要支持**两条数据时效链路**（见第 9 章）：固定规则的近实时链路 + 标签清洗的 T+1 离线链路。
- （数据看板这块我方**无需做**，数据组在单独重建。）

## 2. 用户分群 / Cohort —— 把用户切成一块块

### 是什么
**分群（Segmentation）** = 按条件把全体用户切成一个个人群。每个人群就叫一个 **Cohort（同期群 / 用户分群）**，比如"过去 7 天打过电话但没注册钱包的印度用户"。

切人群靠的是**规则引擎（Rule Engine）**：你像搭积木一样设条件——
> 「`国家 = 印度` **且** `近30天通话时长 > 60分钟` **且** `钱包注册 = 否`」

满足这组条件的所有用户，就构成一个 Cohort，然后你才能对他们做活动。

> **打个比方**：分群 = 给一屋子人发不同的传单。你不会给所有人发同一张，而是"给学生发开学优惠、给上班族发午餐套餐"。Cohort 就是"学生""上班族"这些标签人群。

### Botim 现状（As-Is）
- MoEngage 圈人 = **纯规则引擎，手动圈**（不是 AI 推荐），分三步：① 圈人（可加无穷层嵌套条件，**很难用**）→ ② 定内容 → ③ 定推送时间/条件。
- GZF 举的常用标签：是否 KYC、上次转账时间、是否激活 Wallet、余额等。
- 经验规律：**80% 的活动只用 5~10 个分群**（所以 Phase 1 先覆盖这几个就够）。
- **两条分组路径要分清**（这是个易错点）：
  - **首页"千人千面"卡片**：用 Botim **自有规则**分组，只借 MoEngage 的"下发"能力显示在 App 首页 → **本来就可以自建，不依赖 MoEngage**。
  - **推送等其他触达**：用户分群的**完整路径走 MoEngage**。
- 在 MoEngage 上累计配过约 **800 个活动**（合同 2025-07 签、约一年，≈2~3 个/天）。

### 我们要做什么
- **复刻规则引擎**，把 MoEngage 上 Top 10 实际在用的 Cohort（含底层 SQL/规则 + 当前人数）搬过来（对应数据专项 D13）。
- **叠加 NL2SQL**（见第 9 章）：让运营用大白话"过去30天活跃但没开钱包的菲律宾用户"就能圈人，不用写 SQL。
- **用算法优化分群效果**（Plan 里写的"Cohort 算法"）：从纯手动规则，进化到 AI 辅助找相似人群、推荐高潜人群。

## 3. Campaign 编排（Campaign Orchestration）—— 设计一场活动

### 是什么
**Campaign（营销活动）** = 一次完整的营销行动："对哪群人（Cohort）、发什么内容、走什么渠道、什么时间、发几次"。

**编排（Orchestration）** = 把这些要素组装起来、设定逻辑。当活动不是"发一条就完"，而是有**多步骤、带条件分支**时，就叫一条 **Flow（流程/旅程）**，例如：

```
用户开户  →  等10分钟  →  推送A"欢迎礼包"  →  [点了吗?]
                                              ├─是→ 推送B"立即激活钱包"
                                              └─否→ 等1天 → 短信提醒
```

编排里几个必懂的小概念：
- **A/B/N 测试**：同一群人随机分成几组，发不同文案/Offer，看哪组效果好。这是科学验证、避免"拍脑袋"的核心手段。
- **触发型 vs 批量型**：批量 = "今晚给这 100 万人统一推"；触发型 = "用户一开户就立刻推"（依赖实时事件流）。
- **频次控制**：限制同一个用户一段时间内最多收到几条，避免骚扰。
- **归因窗口（Attribution Window）**：用户收到消息后，多久内发生转化才算"这条消息的功劳"，比如 24 小时 / 7 天。

> **打个比方**：Campaign 编排 = 导演排一场戏。Cohort 是观众群，文案是台词，渠道是舞台，Flow 是剧本的分支走向，A/B 测试是"两个结局都拍出来看观众更喜欢哪个"。

### Botim 现状（As-Is）
- 编排由增长团队**人工**设策略，内容**自审**（主要看效果，无央行等外部强监管细审）。
- 支持 **A/B/N 组、版本微调**。
- **以批量活动为主**，部分实时（如评分、按页面触发）；精确比例待 Growth 确认（资料提示：实时占比 > 30% 则 2 个月内难替换，全 T+1 则难度骤降）。
- 归因窗口约 **1~2 天**（GZF 经验值，非硬性，非瓶颈）。
- **频次控制是明显短板**：Botim 侧**无跨活动去重、无每用户每日上限**，只对推送做**限速**（防系统/页面被打爆）；同一用户一天可能收到多条（赶上就 3 条都收）。

### 我们要做什么
- **内容与推送编排**（我方 3 大核心功能之一）：版面 / 时间 / 内容，支持 A/B/N 组。
- **AI 生成活动文案**（Plan 明确要做）：多语种（印地语/他加禄语/阿语/英语），并能 join 上历史效果数据来学习。
- 可探讨**用大模型（GPT）替代人工编排**（Survey 里 GZF 提到的方向）。
- **补上频次控制 / 去重**——这正好呼应风险点"用户刚转完账就不该再被触达"，是新平台可以比 MoEngage 做得更好的地方。

## 4. 触达（Reach / Messaging）—— 把消息真正发出去

### 是什么
**触达** = 把活动内容真正送到用户面前。常见**渠道（Channel）**：
- **Push（推送通知）**：手机锁屏/通知栏弹的那条。用户在线直接发；离线要走 Google（FCM）/ 苹果（APNS）的三方通道。
- **SMS（短信）**：需要手机号，成本高、到达稳。
- **In-App（站内）**：用户打开 App 时看到的——站内消息、**弹窗（popup）**、页面里嵌的 **H5** 卡片、评分弹窗。
- （Botim **没有 email 渠道**。）

几个关键概念：
- **送达率 / 到达率**：发出去 ≠ 收得到。取决于用户是否在线、设备类型（Android 通常低于 iOS）、是否卸载。
- **Opt-out（退订名单）**：用户说"别再给我发了"，必须尊重，发送前要排除这些人。
- **推送 Token**：手机的"收件地址"。谁掌握 Token 谁就能直接给用户发消息——这是个安全敏感物。

> **打个比方**：触达 = 快递最后一公里。分群是"按地址分拣包裹"，触达是"快递员真正送到门口"。送达率就是"有没有人在家签收"，Opt-out 就是门口贴的"谢绝快递"。

### Botim 现状（As-Is）
- **安全红线**：Botim 拒绝把推送 Token 交给 MoEngage。**最后一步发送始终走 Botim 自有接口**——MoEngage 只能"调一次 Botim API、发一次"，没有直接推送权限。**新平台必须沿用这条边界。**
- **渠道非同一套 API**：In-App 弹窗 = MoEngage SDK 直接渲染（不过 Botim 后端）；Push/SMS = 走 Botim 自有通道。
- **频次**：无系统级上限，仅限速；"一天两三条"指的是活动数量，不是每用户上限。
- **Opt-out**：名单存在 MoEngage、可导出；Botim 开放平台本身不标记退订。
- **送达率**：依赖三方 + 用户是否在线，范围很大（圈到已卸载用户就永远收不到），有追踪，具体数字待 Growth。

### 我们要做什么
- **统一/对接多渠道触达 API**：Push / SMS / In-App，注意各渠道实现不同，要分别对接。
- **沿用 Token 安全边界**：最后一步必经 Botim 接口，不接管 Token。
- **接管 Opt-out 名单**：从 MoEngage 导出并纳入发送前的排除逻辑。
- Shadow 阶段需要一个**测试人群专属通道**，避免影响正式流量（Botim 以前有，现是否仍有待确认）。

## 5. 效果回收与分析（Analytics & Attribution）—— 看有没有用

### 是什么
活动发完，要回答"成功了吗"。核心工具：
- **漏斗（Funnel）**：用户一步步流失的转化路径，如 `收到推送 → 点开 → 进入页面 → 完成转账`，每一步留下多少人。**跨产品漏斗**（如"通话活跃 → 注册钱包 → 首笔汇款"）是 MoEngage 答不了、新平台要能答的。
- **核心指标**：点击率（CTR）、转化率（CVR）、ROI。Botim 口径基本统一：**查看 → 点击 → 最终转化**。
- **A/B 对照**：和"什么都不发的对照组"比，证明活动真的带来了增量，而不是用户本来就会转。

> **打个比方**：效果分析 = 考试后看成绩单 + 错题本。漏斗告诉你"学生在第几道题集体卡住"，A/B 对照告诉你"这套新教材到底比旧的强多少"。

### Botim 现状（As-Is）
- 触达/转化日志**完整记录到用户级**（已读 → 是否转化可追踪），保留时长待确认。
- 回收周期 **1~3 天**（最短 1~2 天），非实时敏感，**不构成瓶颈**。
- 增长团队看 MoEngage 看板；产品侧另用 **Amplitude**（独立埋点、独立采购——"花了两份钱"）。
- **关键利好：MoEngage 数据不回写 Botim**，闭环全留在 MoEngage，所以**没有下游系统依赖、替换不会造成连锁中断**。

### 我们要做什么
- **Campaign 漏斗追踪**（我方 3 大核心功能之一）：每次推送埋点，结果以 NL2SQL 或 dashboard 呈现。
- **行为分析自动化**（Plan）：把那 5~10 张"真有人看"的报表搬到自有 BI，并写算法自动分析。
- 要能回答 MoEngage 答不了的问题（如跨产品漏斗）。

## 7. 产品需求总览：我方到底要交付什么

把三份资料对齐后，需求收敛得相当清楚。

### 7.1 我方 3 个核心功能（来自访谈关键结论）
1. **Cohort 圈人**：复刻规则引擎 + 叠加 NL2SQL。
2. **内容与推送编排**：版面 / 时间 / 内容，支持 A/B/N 组。
3. **Campaign 漏斗追踪**：每次推送埋点，结果以 NL2SQL 或 dashboard 呈现。

围绕这 3 个核心，Plan 把它拆成 5 项工程能力：**Cohort 引擎 · 行为分析自动化 · Flow 活动模板 · AI 文案 · NL2SQL 取数**。

### 7.2 明确"不做"的范围（很重要，避免镀金）
- **数据看板 / Dashboard**：数据组马老板单独重建，我方不做。
- **客服主动外呼、流失用户沟通**：超出 MoEngage 范围，与本项目无关。
- **Email 渠道**：Botim 根本没有。
- **接管推送 Token**：安全红线，永远走 Botim 接口。

### 7.3 优先级排布
- **P0｜先别让日常停摆**：增长团队每天 2~3 个活动、累计约 800 个在跑。第一要务是保证"**圈人 + 触达**"能在新系统跑起来（哪怕半手动），尤其要替代 MoEngage 的筛选规则。**触达（Push + In-App 弹窗）是优先级最高的**，其次分群。
- **P1｜核心闭环 + AI 增量**：规则引擎 + NL2SQL、编排 + AI 文案、漏斗追踪。这是立项的价值所在。
- **P2｜可慢慢迁**：首页千人千面（本就可自建，风险低）、长尾活动模板。

### 7.4 Phase 1 的"北极星指标"（待 Growth 最终确认）
- GZF 给的底线：**至少不低于现状**（"上线后没人抱怨"），增量靠 AI 提升活动量/验证效率。
- 业务背景指标：通话用户→Fintech 渗透率约 **7.5%**，公司今年目标 **10%**（⚠️ 原表写 15%、录音说 10%，**口径待 Growth 确认**）。注意这是**使用方背的业务 KPI，不是工具本身的指标**。
- 产品落点：最想推 **Loan（借贷）**，当前流量最大 **Remittance（汇款）**；通用旅程 `KYC → 激活 Wallet → 向下 cross-sell`。

## 9. 新人必懂名词速查表

| 名词 | 一句话解释 |
|---|---|
| **MoEngage** | 要被替换的营销自动化平台，打通了"埋点→分析→分群→触达"全流程 |
| **埋点 / Event** | App 里记录用户行为的传感器，产生原始事件日志 |
| **画像 / 标签（User Attribute）** | 埋点清洗后算出的用户特征，如"是否KYC""钱包余额" |
| **Cohort / 分群** | 按条件切出的一群用户 |
| **规则引擎** | 像搭积木一样设条件来圈人的工具 |
| **Campaign** | 一次完整营销活动（对谁、发什么、走哪、何时） |
| **Flow** | 带分支/延时/条件的多步骤活动旅程 |
| **A/B/N 测试** | 同群人分组发不同内容，比效果，科学验证 |
| **触达 / Channel** | 把消息发出去；渠道有 Push/SMS/In-App（无 email） |
| **Push Token** | 手机的"收件地址"，安全敏感，Botim 不外给 |
| **Opt-out** | 用户退订名单，发送前必须排除 |
| **归因窗口** | 收到消息后多久内转化才算这条消息的功劳（Botim 约 1~2 天） |
| **漏斗 / Funnel** | 转化路径每一步的流入/流失人数 |
| **CTR / CVR / ROI** | 点击率 / 转化率 / 投入产出比 |
| **Shadow** | 切一小撮流量与旧系统并行对照的低风险验证 |
| **CDP** | 客户数据平台，把各业务线用户数据打通成统一视图——**Botim 目前没有** |
| **ID-Mapping** | 同一用户在通话/汇款/钱包等不同业务线的 ID 是否能对上的映射表（Botim 业务线未打通，待确认） |
| **T+1 / 实时** | T+1=今天处理昨天数据；实时=行为发生即可用。Botim 清洗 T+1，分群可用约小时级 |
| **NL2SQL** | 自然语言转 SQL——运营用大白话就能取数/圈人，本项目重点 AI 能力 |
